# ADR-001: Capas simples para persistencia; el seam de notificación ya cubre el próximo cambio conocido

## Estado
Aceptado — 2026-11-20

## Contexto
Tras integrar **Chain of Responsibility** (validación), **Strategy** (cálculo por categoría) y **Observer** (notificación) sobre el sistema de solicitudes de reembolso (`reembolsos-integrado`), corresponde decidir si el proyecto debe migrar a una **arquitectura Hexagonal completa** (introduciendo interfaces de puerto y adaptadores para persistencia y notificación) o mantenerse en **arquitectura en capas simples**.

Evaluando el criterio de la Guía (sección 6.2 — sistemas que sobrevivirán 3 años o más con cambios frecuentes de infraestructura):
- **Persistencia:** Hoy no existe ningún plan de cambiar de motor de base de datos relacional ni de abandonar Spring Data JPA.
- **Notificación:** El área de Contabilidad anunció para el próximo trimestre una integración mediante API REST externa para programar el pago de las solicitudes aprobadas.

## Decisión
1. **Persistencia — Capas simples:** `SolicitudReembolsoService` continúa dependiendo directamente de `RepositorioSolicitudesJpa` (`JpaRepository`), sin introducir una interfaz de puerto intermedia ni una entidad de mapeo separada. Crear un puerto de persistencia hoy sería una abstracción especulativa (violación de **YAGNI**) sin un caso de uso real que la requiera.
2. **Notificación — Seam existente suficiente:** No se introduce una capa Hexagonal adicional porque `ObservadorCambioEstado` ya actúa como el *seam* de desacoplamiento necesario. El próximo trimestre, `NotificadorContabilidad` podrá reemplazar internamente su `System.out.println` por una llamada HTTP al sistema de Contabilidad sin modificar una sola línea de `SolicitudReembolsoService` ni de los demás observadores.

## Consecuencias
### Positivas
- Se evita código ceremonial innecesario (interfaces espejo, adaptadores y mappers de persistencia sin un segundo proveedor real).
- El único cambio de infraestructura con fecha conocida (API de Contabilidad) ya cuenta con su punto de extensión listo y aislado.

### Negativas
- Si en el futuro surgiera un requisito imprevisto de migrar a un motor NoSQL o a almacenamiento externo, el puerto de persistencia deberá extraerse de forma retroactiva; se asume esa deuda técnica de manera consciente.
- Un revisor que espere simetría absoluta de puertos en todas las dependencias externas podría percibir asimetría si no consulta este ADR.
